# 查询性能分析：N+1 实测

> 测量时间：2026-10-03（本地 Saleor 3.23 实例）
> 方法：Postgres SQL 日志统计单次 GraphQL 请求的真实 SELECT 次数
> 工具：[`scripts/query_count_probe.py`](../scripts/query_count_probe.py)

## 1. 为什么测这个

GraphQL 列表接口天然容易 N+1：列表每行再嵌套子对象（variants、pricing、collections…）
时，ORM 若逐行取数，SQL 次数会随行数线性增长——页大小从 5 涨到 100，
SELECT 次数也会从个位数涨到上百次。

Saleor 3.x 内部使用 DataLoader 做批量加载。**这是否真的生效，不凭文档推断，
用 SQL 日志实测**：如果查询次数与页大小无关，即排除 N+1；如果线性增长，
则按嵌套字段逐个定位。

## 2. 测量方法

1. 临时打开数据库语句日志：`ALTER SYSTEM SET log_statement = 'all'` 并 `pg_reload_conf()`
2. 先测 3 秒空闲窗口，得到环境背景噪声（本次实测为 0 次）
3. 每个场景在独立时间窗内发送一次 GraphQL 请求，等待日志落盘后
   统计 `docker logs --since <窗口起点>` 中 `statement: SELECT` 的行数
4. 测量结束立即恢复 `log_statement`，不在数据库留配置残留

> 为什么按行计数可靠：Postgres 每条语句产生一行 `... LOG: statement: SELECT ...`，
> 语句内的换行只是后续物理行，不再含 `statement:` 前缀，不会重复计数。

## 3. 实测数据

被测环境：本地 Docker Compose 部署的 Saleor 3.23，商品总数 29、变体总数 81。
同一形态分别以 `first=5` 与 `first=100` 请求（后者实际返回全部行）：

| 查询形态 | first=5 | first=100（返回 29/81 行） |
| --- | --- | --- |
| products + variants + pricing | 10 次（5 行） | 9 次（29 行） |
| products + variants + pricing + collections + category | 10 次（5 行） | 10 次（29 行） |
| productVariants + product（反向嵌套） | 3 次（5 行） | 3 次（81 行） |

关键观察：

- 三种形态下，**SELECT 次数均不随行数增长**：行数从 5 涨到 29 / 81，
  查询次数保持在个位数不变；
- 若存在 N+1，`first=100` 应出现约 100+ 次 SELECT（每行一次子查询），
  与实测相差一个数量级以上。

## 4. 结论

1. **未复现 N+1**：Saleor 3.23 的 DataLoader 批量加载在上述三种典型嵌套
   形态下均有效，列表查询次数与页大小解耦（variants+pricing 形态恒定约 9-10 次，
   反向嵌套恒定 3 次）。
2. **测试动作的价值在于「验证」而非「假设」**：初判列表嵌套查询存在 N+1 风险，
   实测后以数据排除。该结论已作为背景知识固化在用例设计中——性能关注点
   从「逐行取数」转移到「嵌套深度带来的序列化开销」。
3. **回归建议**：升级 Saleor 版本、新增自定义 app / 字段解析器时，
   应重跑 [`scripts/query_count_probe.py`](../scripts/query_count_probe.py)，
   查询次数显著增长即为 N+1 回归信号。

## 5. 局限性

- 仅覆盖本地实例的三种查询形态，未覆盖全部 429 个操作；
- 本地数据量（29 商品 / 81 变体）远小于生产，DataLoader 在更大数据量下的
  表现需在类生产环境重测；
- 本方法统计语句次数，不衡量单条语句的扫描成本（如缺索引导致的慢查询），
  后者属于 [`docs/性能测试报告.md`](性能测试报告.md) 的压测范畴。
