# Saleor 接口性能压测报告

> 执行时间：2026-10-03 00:44 – 00:57（本机时间）
> 被测版本：Saleor 3.23（本地 docker compose 部署）
> 压测工具：Apache JMeter 5.6.3
> 计划文件：[perftests/saleor-perf.jmx](../perftests/saleor-perf.jmx)

## 1. 测试目标

1. 只读查询（商品列表）在并发下的响应时间与吞吐拐点。
2. 结算写链路（创建购物车 → 地址 → 配送 → 支付 → 回收）在并发下的稳定性与衰减幅度。
3. 压测全程零数据残留（不留购物车 / 订单污染环境）。

## 2. 被测环境

| 项 | 值 |
| --- | --- |
| 主机 CPU | AMD Ryzen 9 7945HX，16 核 / 32 线程 |
| 主机内存 | 15.7 GB |
| Docker 可用内存上限 | 3.818 GiB（api / worker / db / cache / dashboard / jaeger 共用） |
| 运行期内存占用 | api 446 MiB、worker 784 MiB、jaeger 308 MiB、db 48 MiB、cache 9 MiB |
| 接口地址 | http://localhost:8000/graphql/ |
| 渠道 | default-channel |

> 关键约束：所有容器共享约 3.8 GiB 内存上限，且压测机与被测服务同机竞争 CPU。
> 因此本报告的绝对值只代表「单机本地部署」的性能水位，不等价于生产环境容量。

## 3. 测试方案

### 3.1 场景

| 场景 | 链路 | 鉴权 | 说明 |
| --- | --- | --- | --- |
| A 商品列表查询 | `products` | 匿名 | 模拟游客浏览，只读，样本量最大 |
| B 结算写链路 | `checkoutCreate → 收货地址 → 账单地址 → 取配送方式 → 选配送 → 取应付金额 → 创建支付 → checkoutDelete` | 管理员 Token | 每轮自回收，8 个请求为一个迭代 |

两个线程组串行执行（`serialize_threadgroups=true`），避免读写负载互相干扰。

### 3.2 加压方式

单档爬坡 5 s、持续 20 s，逐档提升并发：**5 → 10 → 20 → 50**。
setUp 阶段解析一个「有定价的变体 id」并登录一次取 Token（两者经 `props.put()` 提升为全局属性，供后续线程组跨组读取）。

### 3.3 清理机制

1. **轮内回收**：场景 B 每轮结束时调用 `checkoutDelete` 删除自己创建的购物车。
2. **兜底清理**：tearDown 线程组扫描 email 以 `perf-` 开头的 checkout 并删除。
   持续时间到点时最后一轮可能停在「创建之后、删除之前」，故必须有这层兜底。

### 3.4 断言口径

HTTP 状态码恒为 200，失败藏在两层 errors 中，断言同时覆盖：

- 顶层 `errors`（GraphQL 语法 / 字段 / 权限错误）
- payload 内 `errors` 数组（业务错误，带 code）

> 权限拒绝（如匿名调用 `checkoutDelete`）属于**顶层** errors 且 `data` 为 null，
> 只看 payload errors 会把失败误判为成功——这是本工程踩过并已修正的坑。

## 5. 分析与结论

### 5.1 吞吐在 10–20 并发见顶

吞吐从 5 并发的 17.6/s 升到 10 并发的 21.4/s，20 并发基本持平（20.8/s），
50 并发反而回落到 16.7/s。**系统容量拐点在 10–20 并发之间**，超过后进入排队区。

### 5.2 延迟增长呈超线性

平均延迟：5→10 并发 ×1.6，10→20 并发 ×2.0，20→50 并发 ×3.0。
50 并发时 p95 达 7929 ms、最大 14564 ms，而吞吐并未提升——
典型的资源饱和特征：请求没有失败，而是在队列里等待。

### 5.3 写链路衰减远大于读链路

以平均延迟计，5→50 并发：

- PRODUCTS（读）：207 → 1950 ms，×9.4
- SHIPPING_ADDRESS（写）：361 → 8037 ms，×22.3
- CHECKOUT_CREATE（写）：475 → 3171 ms，×6.7

地址类 mutation 衰减最剧烈（p95 13994 ms），因为它同时触发校验、税率与配送区域计算等重逻辑。
纯查询类接口（`PAYMENT_CREATE` / `CHECKOUT_DELETE`）在 50 并发下仍稳定在 160–260 ms，
说明瓶颈不在网络与 GraphQL 解析层，而在写路径的业务处理与数据库写入。

### 5.4 与功能用例阈值口径的对照

功能测试工程对单接口的响应时间阈值为 **3000 ms**（`SALEOR_MAX_RESPONSE_MS`，见 `config.py`）：

| 并发 | 平均 | p95 | 是否满足 3000 ms 阈值 |
| ---: | ---: | ---: | --- |
| 5 | 253 | 529 | 满足 |
| 10 | 412 | 906 | 满足 |
| 20 | 832 | 2229 | 平均满足，p95 仍满足 |
| 50 | 2501 | 7929 | **p95 超阈值 2.6 倍** |

结论：本地单机部署在 **20 并发以内**可满足功能测试的 3000 ms 口径；
50 并发下平均延迟勉强达标但长尾严重超标。

### 5.5 稳定性

四档共 3198 个业务采样，**错误率 0.00%**，无 4xx/5xx、无 GraphQL 顶层错误、无业务错误。
JMeter 响应超时设置为 30000 ms，观测到的最大耗时 14564 ms 未触顶，
说明系统在过载时表现为「变慢」而非「失败」，未出现连接拒绝或崩溃。

## 7. 风险与改进建议

1. **提高容器内存上限**：当前 3.8 GiB 供 6 个容器共用，worker 已占 784 MiB。
   若需验证更高并发，应先把 Docker 内存上限调至 8 GiB 以上，否则测的是内存压力而非应用容量。
2. **压测机与服务分离**：同机竞争 CPU 会同时压低客户端与服务端表现，建议压测客户端另置一台机器。
3. **引入数据库连接池与缓存指标**：建议在压测时采集 PostgreSQL 连接数、慢查询与 Redis 命中率，
   以定位写路径的具体瓶颈（当前只有端到端耗时）。
4. **补充分级负载**：可在 20 与 50 之间增加 30 并发档位，更精确地定位拐点。
5. **生产容量评估需重测**：本报告为单机本地部署水位，生产环境需在独立、资源充足的集群上重测。

## 8. 复现方式

```bash
# 单档
jmeter -n -t perftests/saleor-perf.jmx -q perftests/perf.properties \
       -Jthreads=20 -Jrampup=5 -Jduration=20 -l perftests/results/grad-20.jtl

# 汇总（把 grad-<并发>.jtl 放在同一目录即可自动识别档位）
python perftests/analyze_results.py --dir perftests/results
```

参数含义、场景设计与已知约束详见 [perftests/README.md](../perftests/README.md)。

压测计划的自洽性由工程自检第 17 项机械校验（请求体 JSON 合法性、GraphQL 语法与根字段存在性、变量声明完整性），
见 `scripts/selfcheck.py`。
